AGENT ENGINEERING / 知识概览

一页理解 AI Agent 工程

从“模型能提出下一步”到“系统能完成一项任务”，中间需要哪些工程能力？这页按我在项目和实习中遇到的问题，整理一条理解主线。

目标与验收 → 获取上下文 → 规划与工具调用 → 执行并更新状态 → 验证结果 → 用失败样本改进

这是一种阅读框架，各环节可以反复迭代。具体系统可能采用固定工作流，也可能让模型动态决定下一步。

如果你刚入门，可以从头读；如果正在做项目，可以直接检查下面六个问题。框架的价值在于把每个概念对应到具体责任与验证方式。

1. 模型提出调用后，谁负责真正执行？

Function Calling 让模型按约定的工具描述提出调用名称与参数。应用程序需要解析请求、检查参数和权限、执行工具，再把结果返回给模型。工具描述应说明适用场景、参数含义和失败状态，避免把模糊的自然语言意图直接交给底层接口。

MCP 提供应用与外部服务交换工具、资源等能力的协议接口。接入协议之后，应用仍需决定加载哪些能力、怎样处理返回结果，以及何时允许执行。MCP 的架构定位见官方架构文档 ↗。

项目里怎么检查：遇到设备离线、参数越界或接口超时，调用层应返回可判断的状态；模型输出“已完成”之前，还应有实际执行依据。

继续阅读：Function Calling · MCP 与工具调用

2. 当前这一步，模型需要知道什么？

RAG 主要解决从资料中取回相关证据的问题。检索结果能否支持当前任务，还取决于文档解析、切分、过滤、排序和最终上下文组装。混合检索可以结合关键词匹配与语义相似度；RRF 按排名融合多路候选，是否有效需要放到固定查询集上比较。

在我的工程理解中，上下文工程还包括任务目标、工具说明、当前状态、代码库约束和已产生的证据。每一步应读取有来源、符合权限且与任务相关的信息；长期记忆还需要考虑时效、作用范围和更新方式。

案例：GUI 知识库把节点、动作与完整路径一起保存，避免不同页面上的“添加”被当成同一功能。检索失败时，可以沿“入库 → 召回 → 排序 → 组装 → 生成”追踪预期证据首次丢失的位置。

继续阅读：GUI 知识构建 · RAG 失败排查 · 检索与上下文系列

3. 哪些步骤由程序确定，哪些留给模型判断？

流程明确时，可以用程序预定义步骤与分支；路径依赖任务和中间结果时，可以让模型动态规划。Anthropic 的工程文章 ↗按控制路径区分 Workflow 与 Agent，并建议从满足需求的简单方案开始，再根据任务表现增加复杂度。

Planner + Executor 将“提出计划”和“执行计划”分开。结构化计划适合表达动作、依赖、前置条件和预算，执行器负责按接口约定调度工具。Multi-Agent 则进一步划分职责或上下文，但也增加交接、通信和状态同步的成本。

案例：智能家居仓库用 LangGraph 保存各阶段结果，并根据占用状态、校验结果和重试次数选择后续路径。判断设计是否合理，要看分工是否清楚、失败如何返回，以及任务结束时有哪些验收依据。

继续阅读：结构化计划与执行器 · 智能家居工作流 · 工作流与多 Agent 系列

4. 任务中断后，系统知道已经做过什么吗？

State 描述当前任务的目标、步骤、产物、失败和预算。Checkpoint 保存流程状态，帮助恢复执行。LangGraph 的持久化文档 ↗还区分线程内状态检查点与跨线程持久数据，它们各自服务不同的记忆范围。

恢复执行还需要核对外部动作。请求可能已经写入成功，只是回执没有收到；此时直接重试可能重复操作。工程上需要结合目标服务能力，保存稳定的操作编号、结果回执或目标版本，区分成功、失败和结果未知。

项目里怎么检查：在测试服务写入成功后模拟回执丢失，再恢复同一任务。观察外部状态、操作回执和本地完成记录是否一致；无法确认结果时，应保留未知状态并交给人核对。

继续阅读：检查点与幂等 · 重试、回滚与重规划

5. 用什么证据判断结果已经完成？

验收条件应尽量落到可观察的结果：文件是否生成、数据是否更新、代码是否通过测试、设备是否达到预期状态。能够确定判断的条件可以用程序断言；开放性的表达质量可以辅助使用模型评审，并保留不确定性和人工复核入口。

案例：ReproLab 用 Dataset → Run → Artifact → Claim 记录输入、执行、成果与结论。仓库中的哈希实现 ↗把代码、输入和环境共同纳入执行身份；复现模块 ↗核对环境、重跑代码并比较产物，帮助定位结果变化。

项目里怎么检查：为每条关键结论找出对应输入、执行记录与验收结果；改动代码或数据后，确认旧验证是否仍然适用。

继续阅读：ReproLab 数据血缘 · 确定性结果比对

6. 一次失败，怎样变成下一次改进的依据？

Trace 保存一次任务的上下文、计划、工具参数、执行结果与状态变化，帮助区分知识、规划、工具和验证问题。Benchmark 把任务、输入与验收条件固定下来，用于比较版本。Badcase 则是需要重现、定位并补入回归的具体失败样本。

指标需要明确统计对象。Top5 路径命中率衡量候选检索是否包含目标路径；端到端完成率衡量整个任务是否满足验收条件。知识库里的应用、节点和指令数量描述覆盖规模，应与执行效果分别呈现。比较方案时，还应同时观察成本、延迟和人工介入。

项目里怎么检查：固定一批任务和验收条件，记录模型、提示词、工具与代码版本；每次只围绕可归因的改动比较结果，并保留未参与调优的任务检查泛化。

继续阅读：失败分层与 Trace · 设计回归任务集 · 评测与可靠性系列

把几个常见术语放回工程位置

Agent
围绕目标获取反馈、选择动作并推进任务的系统。模型参与决策，应用负责状态、执行与约束。
Harness / Runtime
承载 Agent 执行的外围机制。本文用它指代工具接入、上下文、任务状态、预算、恢复和验证等能力；不同项目的范围会有差异。
Guardrail / Validator
对输入、动作或结果实施约束和检查。设计时要明确检查对象、拦截位置，以及失败后由谁处理。
Memory / Context
记忆提供可跨步骤或跨任务保留的信息；上下文是当前模型调用实际获得的信息。保存的信息仍需经过选择、权限与时效检查才能用于本次任务。

从自己的项目开始梳理

选一个任务，写清目标与验收条件，画出信息、计划、工具和状态的流向，再加入一次失败。检查每一步输入从哪里来、动作由谁执行、结果由谁确认，以及中断后从哪里继续。
