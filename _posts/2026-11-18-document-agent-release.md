试用群里有人说：“以前能查到的测试环境发版清单，现在少了构建编号。”总完成率还是 75%。如果只看仪表盘的这一个数，团队可能继续放量。把请求拆开能看到两次变化：新版本终于听懂了“怎么上线”，同时有一组原本正常的发版问题开始失败。多成功一条，也多失败一条，总数正好抵消。

[第三篇](/2026/11/18/document-agent-regression/)用固定测试比较配置。这里接着往线上想一步：**发布后看到什么，才能决定继续观察、暂停扩大范围，还是切回旧配置？** 我们用本地模拟来对照同一批只读请求，并把失败追到真正变化的索引快照。

## 先让一次请求能追到发布版本

发版时给实际运行的组合一个 ID。代码版本之外，模型标识、提示词、工具接口、权限策略、索引快照、上下文预算都可能影响结果。一个发布组合里如果存在按工作区路由的索引，要记录这一条请求实际命中了哪个快照。只写“当前线上是 18”，定位时看不出来是不是某个工作区受影响。

这个练习有两组配置：`release-17` 使用旧字面查询与完整索引；`release-18` 增加“上线 → 发版”的别名，同时把 `beta` 工作区指向包含不完整数据的索引。其他工作区继续用完整快照。这种同时发生的变动在接入知识库时并不少见：应用配置改了，同一批快照也刚好换过去。

| 字段 | 旧版 | 候选版 |
| --- | --- | --- |
| 同义词 | 原词执行 | “上线”映射到“发版” |
| 默认工作区索引 | `handbook-17` | `handbook-17` |
| beta 工作区索引 | `handbook-17` | `handbook-18-incomplete` |
| 模型与工具 | 同一模型替身与工具接口 | 同左 |

线上要把发布记录与单次执行记录对上号。最低限度保留可关联的任务 ID、版本、实际快照、用户场景、工具命中的证据 ID 和最终状态。若两版本对比运行，还需要一个共同的请求标识。需要追问范围、用户本来就无权访问、工具异常，分别记录成不同状态。

## 同样的 3/4，是怎么组成的？

把 <a href="/assets/examples/document-agent/agent.mjs" download>agent.mjs</a> 和 <a href="/assets/examples/document-agent/release.mjs" download>release.mjs</a> 放在同一个目录，执行 `node release.mjs`。六条请求先在基线跑，再用候选运行同样的输入。两条只检查是否正确停止，另外四条才算进“能交付清单”的分母。

| 请求 | 基线 | 候选 |
| --- | --- | --- |
| 默认工作区问“测试环境怎么发版” | 完整 | 完整 |
| beta 工作区问同一个问题 | 完整 | 缺构建编号 |
| 默认工作区问“测试环境怎么上线” | 缺资料 | 完整 |
| 授权用户查生产环境发版 | 完整 | 完整 |
| 未授权用户查生产环境 | 正确停止 | 正确停止 |
| 用户没有指定环境 | 正确追问 | 正确追问 |
| 应交付清单的请求 | **3/4** | **3/4** |
| 关键切片“常规测试环境发版” | **2/2** | **1/2** |

统计前先明确你在量什么。这个案例里的完成是“有权限、环境已确认，且通过必需项验收”。合理追问和拦截越权请求各有自己的断言。把它们都纳入一个完成率，用户问题类型分布变了，指标也会跟着变，容易误判版本差异。

## 用同一条请求定位是哪一步变了

对照 `release-beta` 的两次记录，先看证据，再看最后状态：

```json
{
  "caseId": "release-beta",
  "before": {
    "snapshot": "handbook-17",
    "status": "ready_for_review",
    "evidence": ["test-v2#smoke", "test-v2#build"]
  },
  "after": {
    "snapshot": "handbook-18-incomplete",
    "status": "needs_evidence",
    "evidence": ["test-v2#smoke"]
  },
  "firstDifference": "search_results"
}
```

工具结果先变了，验收随后才拒掉清单。候选配置改了同义词，但这个请求用的是原词“发版”，根本没走别名。在这个模拟里，进一步查快照可以看到 `test-v2#build` 没同步到新索引。实际值班遇到这个结果，先核对有效版本和入库状态，再看是否是权限过滤、排序或上下文裁剪造成的。只看到两个版本的命中不同，证据还不足以直接归因给某个模型。

## 灰度门禁与回滚后的核对

练习的决策有固定优先级。候选出现越权证据，或应停止的请求继续执行，先停止候选；关键切片的配对样本不够，就继续收集；已经有最低样本且出现原来能完成、现在失败的关键用例，就切回旧版。这里的“两条”只是用于演示逻辑的门槛。真实上线时要先按流量和失败代价确定样本窗口、各角色分组、质量和延迟的阈值，并记录做决定时实际有多少样本。

| 阶段 | 实际看什么 |
| --- | --- |
| 影子运行 | 基线继续服务，候选只读并记录。两版对同一请求比较工具结果、完成状态和耗时 |
| 小范围灰度 | 按用户或工作区稳定分流，确认关键角色、环境和文档版本都有样本，再扩大范围 |
| 切回 | 把新任务指回上一个已验证可用的发布组合，保留候选运行的任务 ID 供排查 |
| 确认恢复 | 用原失败请求和相同权限再跑一遍，核对实际生效的版本、索引和引用 |

脚本给出 `rollback_critical_slice`，再用旧配置重放 `release-beta`，确认构建编号确实回来了。加上 `--fixed-index` 后保留新的同义词规则，让 beta 重新使用完整快照。关键切片回到 2/2，决策变成 `keep_observing`。这些都是本地样本。线上如果旧索引已被下线，或包含已撤回的权限与文档，直接切回也不成立。执行前检查旧依赖仍可用，并继续按当前授权校验；必要时可以暂停生成草稿，仅保留查询或人工入口。

如果这次发布也启用了保存工具，切回应用只改变后续请求和任务的处理路径。先用[写入恢复中的操作编号和回执](/2026/11/18/document-agent-durable-write/)核对已经在执行的任务，再决定哪些可以恢复、哪些需要人工确认。已经写出的草稿需要走独立的处理流程。回滚后把 `release-beta` 加进离线回归，同时补一条同步校验：每个工作区的可见快照是否包含业务要求的必需主题。
