有个同事问“测试环境怎么上线”，Agent 说缺少资料。他再问“测试环境怎么发版”，就拿到了清单。文档没有改，同一用户的权限也没变。用这个问题比较两个模型，很可能会把检索里的缺口错归给模型；只改一条同义词规则，然后依次点几下界面，也很难知道有没有引入新问题。

这一篇跟踪一条具体的漏检索。我们先用本地执行记录找出出错的位置，再把它变成固定用例。评测时只改查询别名，文档、权限、模型替身和验收代码都用同一份。

## 第一个错在哪一步？

把失败那次执行拆开。模型替身从用户问题中选了“上线”。搜索工具按环境和权限划过一遍，使用字面匹配，因此返回空数组。模型收到的是空结果，后面的验收器再按缺少必需主题返回 `needs_evidence`。这条链路里，程序诚实地报告了找不到资料。该修的是检索词和文档词汇之间的差异。

| 观察位置 | 失败时看到了什么 | 接下来查哪里 |
| --- | --- | --- |
| 模型调用 | 请求了 `search_docs`，查询词是“上线” | 工具选择正确，先看检索 |
| 工具结果 | 空命中 | 对照权限、当前版本和字面匹配 |
| 模型第二轮 | 拿到空结果，来源 ID 是空数组 | 结果回填正常 |
| 验收 | 两个必需主题均缺失 | 输出状态合理，保留该行为 |
| 候选配置 | 查询别名把“上线”映射到“发版” | 验证两条当前片段是否都回来 |

这一次可以先用最小改动验证方向，随后再考虑词典、混合检索或模型改写。真实知识库里“上线”也可能指服务恢复、功能开关放量等动作。若准备把别名推广到别的索引，应该先加“恢复服务上线”和“功能向谁放量”一类反例，避免把本来不同的词强行合并。

## 一条用例要同时写出结果和允许看到的资料

单独断言 `status === "ready_for_review"` 有个漏洞：只要草稿能拼出来，即使用了别的环境的资料也会通过。我们给每条用例留两份期望，各自拦不同的退步。

```javascript
{
  id: "test_synonym",
  slice: "retrieval",
  env: "test",
  groups: ["dev"],
  question: "测试环境怎么上线",
  expected: "ready_for_review",
  visibleIds: ["test-v2#smoke", "test-v2#build"],
  expectedIds: ["test-v2#smoke", "test-v2#build"]
}
```

`visibleIds` 是允许送进模型的片段，评测脚本从 `search` 记录取集合比对。即使模型最终没引用不该看到的内容，前一阶段把它送进了上下文也要判失败。`expectedIds` 是交付物必须按顺序使用的来源。没有环境时还断言模型调用次数为 0；重复查询时断言两轮结束。对这种输出能确定判断的例子，直接写断言比抽一句“回答不错”有用。

固定用例有十条。每条代表一个需要维持的行为：

| 用例 | 期望 | 它能发现什么 |
| --- | --- | --- |
| `test_release` / `prod_release` | 各拿到本环境指定的两条证据 | 版本过滤、角色权限、必需项顺序 |
| `test_synonym` | “上线”也找到相同证据 | 字面检索漏召回 |
| `partial_checklist` | `needs_evidence` | 已有两条资料，模型只交了一项 |
| `invented_id` | `invalid_draft` | 提交从未召回的旧版 ID |
| `prod_denied` | `needs_evidence`，命中为空 | 越权片段进入工具返回 |
| `no_environment` | `needs_environment`，零次模型调用 | 进入循环前漏了澄清 |
| `conflicting_handbooks` | `conflicting_evidence` | 两份当前资料互相冲突仍被交付 |
| `repeat_tool` | `repeated_query`，第二轮停 | 模型重复同一调用 |
| `search_down` | `search_unavailable` | 把服务不可用误当资料不存在 |

## 跑两遍，看逐条差异

把 <a href="/assets/examples/document-agent/agent.mjs" download>agent.mjs</a> 和 <a href="/assets/examples/document-agent/eval.mjs" download>eval.mjs</a> 放在同一个目录，执行 `node eval.mjs`。脚本在每条用例里重新构造模型替身和索引配置。基线用字面检索，候选只增加 `{ "上线": "发版" }`。下面是实际运行的结果，省略了通过标记和期望字段：

```json
{
  "baseline": "9/10",
  "candidate": "10/10",
  "improved": [
    {
      "id": "test_synonym",
      "before": { "status": "needs_evidence", "evidence": [] },
      "after": {
        "status": "ready_for_review",
        "evidence": ["test-v2#smoke", "test-v2#build"]
      }
    }
  ],
  "regressed": [],
  "blocked": []
}
```

9/10 和 10/10 是这十个固定输入上的**用例通过数**。拒答正确和按要求交付草稿都能计通过，不能把数字直接叫“Agent 回答准确率”。这里真正让人信服的是那一条变化：基线没搜到资料，候选搜回两个应有片段，其他行为未变化。门禁看逐条通过情况；出现回归或候选有不满足预期的样本，脚本非零退出。这样 CI 可以拦住“总分上升，但有一个角色权限坏了”的改动。

## 怎样把本地回归接到上线？

先决定哪类变动必须跑哪批用例。更新索引时，固定一批权限与版本矩阵，看工具返回阶段；更新模型时，固定索引做几次重复采样，看工具选择、来源覆盖、耗时和输出失败分布；更新验收逻辑时，用固定的工具轨迹测试缺项、错误引用和冲突。把每次运行的索引版本、模型标识、工具定义和评测集版本一起记录，后面才有可能对照。

首次试用可以让两种检索配置处理同一批**只读**请求，候选结果先只做记录。观察口语问题采样里缺证据的比例、错误引用、超时和任务耗时分布。设门槛时写明分母，例如缺证据率只统计“环境已确认且检索已运行”的请求，否则澄清次数变化也会影响数字。上线前准备一个能切回旧索引配置的开关；一旦出现越权片段或错误引用，先保留能定位差异的任务 ID 和版本，再回滚候选配置。

不要把模拟数据的结果直接外推到真实文档。把线上失败整理进评测时，保留授权后的必要输入和预期状态，删掉与复现无关的内容。有业务语义判断的样本单独标注，有确定答案的继续用断言。半年后回看，一个名字清楚、能指出哪阶段退步的用例，通常比一张只有平均分的图表更快帮你找到原因。
