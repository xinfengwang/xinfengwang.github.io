手机应用的功能分散在多层页面。同一个目标也有多种说法，例如“添加闹钟”“设个闹铃”。这个项目关注的是：如何整理界面里的操作入口、路径与功能语义，让这些信息可以被浏览、检索，并用于生成多样的自然语言指令。

公开仓库包含系统设计文档与内置处理后数据的展示页面。下面先介绍知识构建流程，再说明它与自动执行之间的边界。

## 从截图整理出 GUI 交互树

采集阶段通过 ADB 获取手机截图，再用多模态模型解析界面元素、功能和预期变化。探索以深度优先遍历组织，页面导航和特殊交互由人工处理。

可以将一条操作路径写成：

```text
时钟 → 闹钟 → 添加闹钟
```

交互树保留入口之间的层级关系。单屏解析用于识别功能入口，多屏增量解析用于处理长列表，并参考已识别内容减少重复。这个过程包含人工操作，不能直接称为完全自主的应用探索。

## 从树节点到可检索记录

树适合表达结构，检索则需要能独立比较的记录。因此知识处理流水线会提取节点、动作和完整路径，并按节点名称、动作与路径去重。

下面是解释字段关系的示例，不来自真实采集记录：

```json
{
  "node_name": "添加闹钟",
  "action_type": "click",
  "path_str": "时钟 > 闹钟 > 添加闹钟",
  "intent_name": "设置闹钟",
  "generated_queries": ["新建一个闹钟", "帮我添加闹铃"]
}
```

保留路径很重要：两个页面上的“添加”可能对应完全不同的功能。只有结合所在应用、上级页面和具体动作，节点描述才有足够的上下文。

## 用意图与多样表述连接用户语言

语义增强阶段为操作节点生成自然语言指令和意图关键词，再按用户目标归组，将意图标签回写到扁平知识库。

指令泛化覆盖清晰、同义、模糊、含噪、多步依赖与跨应用六类表述。这里的“多步”和“跨应用”指生成的数据类型，不代表系统已经完成了相应操作，更不能直接作为执行成功率的证据。

## 检索与展示分别解决什么问题

仓库文档描述了 jieba 分词与 BM25 检索。展示页面则支持按应用、功能意图、操作节点与泛化指令逐层浏览，也可以搜索和排序。

关键词检索适合匹配明确功能名。若后续加入向量检索与融合排序，需要用固定查询集比较召回质量；这属于可探索的扩展，不能写成当前公开仓库已实现的能力。

## 分阶段保存，便于恢复和排查

采集、解析、增强和结构化分别保存中间结果。采集阶段保存探索状态，增强阶段保存处理进度，模型调用失败时使用重试与退避。

这种拆分让问题更容易定位：采集漏了页面，就回到采集阶段；路径重复，就检查解析去重；指令表达不准确，则检查增强结果。每个阶段的产物也能供下一轮增量处理使用。

## 展示规模与评测结果要分开

仓库记录的展示快照包含 47 个应用、5,285 个操作节点、321 个意图分类和 37,166 条基础指令。这些是收集与处理规模，不是独立评测结果。约 95,000 条泛化变体是按每节点 18 条推算的规模，不应作为实测完成量。

要判断知识库是否真正帮助 GUI Agent，还需要另行定义查询集、相关路径标注、检索指标和执行任务，并记录失败条件。当前文章不据展示数量推断自动操作效果。
